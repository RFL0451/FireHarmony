Wiki: what happens to the data

This page documents every step between the raw satellite feeds and the points, charts and CSV files you see on the dashboard. It is written for users who want to trust (or audit) the numbers.

1. Data sources

  • NASA FIRMS (Fire Information for Resource Management System), near-real-time API: MODIS_NRT (Terra/Aqua, ~1 km pixels, record since 2000) and VIIRS_SNPP_NRT (Suomi NPP, 375 m pixels, since 2012).
  • The FIRMS area API accepts a bounding box and a range of at most 5 days per request. Longer ranges are rejected (HTTP 400).
  • Each detection is a point with: latitude/longitude, acquisition date and time (UTC), brightness temperature (K), FRP — fire radiative power (MW), confidence, satellite and a day/night flag.
  • Demo mode: if the API key is missing or the request fails, the app falls back to synthetic detections modelled on FIRMS fields (the status line says “Showing demo data (synthetic)”). Demo numbers are not real fire counts.
  • Base maps (map tiles drawn under the detections; they are not fire data): OpenStreetMap contributors for the local-language map; Esri, DeLorme, NAVTEQ (Esri World Street Map) for the English-label map; Esri World Imagery for the satellite view.

3. Harmonization (js/dashboard.js → harmonize())

Goal: decide which MODIS and VIIRS detections are the same fire, without double-counting. We use a Greedy Spatial-Temporal Matching with Grid Bucketing algorithm.

Step-by-step algorithm:

  1. Grid Bucketing (Optimization): Comparing every MODIS point to every VIIRS point is slow (O(N×M) complexity). To speed this up, the world map is divided into a grid of 0.05° squares (~5.5 km at the equator). All VIIRS points are placed into these cells using a JavaScript Map.
  2. Candidate Search: The algorithm takes each MODIS point and looks only in its native cell and the 8 adjacent cells (horizontal, vertical, diagonal). This prevents missing matches that lie just across a cell boundary while drastically reducing the number of checks.
  3. Time Filter: For each VIIRS point in the neighbouring cells, the time difference is checked. If the difference is greater than the selected "Max time gap" slider, the VIIRS point is discarded.
  4. Distance Filter: If the time fits, the exact distance is calculated using the Haversine formula (accounting for Earth's curvature). If the distance is greater than the selected "Max distance" limit, it is discarded.
  5. Greedy Selection: The algorithm doesn't just take the first matching point. It evaluates all candidates and selects the VIIRS point that is closest to the current MODIS point.
  6. 1-to-1 Matching: Once the best pair is found, the VIIRS point is marked as used in a Set. This ensures one VIIRS point cannot be matched to multiple MODIS points, which is critical for fair statistics.
  7. Result Formation: The pair is saved. Points left without a pair (MODIS-only or VIIRS-only) are kept as single-sensor detections because they contain unique information.

Why this algorithm?

  • Speed: Thanks to Grid Bucketing, the algorithm runs in roughly linear time O(N), enabling instant recalculation when the user moves the sliders on the dashboard.
  • Geometric Accuracy: The Haversine formula ensures correct distances in kilometers.
  • Practicality: Nearest Neighbor matching is a classic approach that works well for fires since a fire has a clear physical center.

Limitations: A greedy algorithm does not guarantee a global optimum (unlike the Hungarian algorithm), but it provides an excellent balance between speed and accuracy for dense spatial-temporal points in a web browser.

4. Static heat source filter (js/persistent.js)

  • The map is bucketed into cells of roughly the chosen size (0.5–3 km). If the same cell has detections on at least N distinct UTC days (default 3), every point in it is flagged persistent.
  • Persistent points are drawn with a dashed grey ring and reduced opacity, and can be hidden with the “Hide persistent hot spots” checkbox. Typical members: gas flares, industrial furnaces, active volcanoes.

5. Fire likelihood score (js/confidence.js)

Levels: High ≥ 70 (very likely a real fire), Medium 40–69 (probably a fire, cross-check), Low < 40 (uncertain — possible false alarm). This is a heuristic for triage, not a calibrated probability.

6. Anomaly watch

  • Daily counts of unique harmonized detections are compared against the selected period: a day with a z-score ≥ 2 (at least 2 standard deviations above the period mean) is anomalous. Needs ≥ 7 days of data.
  • The regional table repeats the same test per continent-scale region and flags regions whose peak day is anomalous with ≥ 5 detections.

7. Map, colors and exports

  • Map labels: the layer control in the top-right of the map switches between English labels (Esri World Street Map tiles), local-language labels (standard OpenStreetMap) and unlabeled satellite imagery (Esri World Imagery).
  • Palette: MODIS vermillion #D55E00, VIIRS blue #0072B2, harmonized amber #E69F00 — chosen from the colorblind-safe Okabe–Ito palette so the three classes stay distinguishable for most viewers.
  • CSV exports include all normalized fields plus matched, persistent and the fire-likelihood level/score.

8. Known limitations

⚠ FIRMS near-real-time data is capped at 5 days per request and has no long history in this app; the demo dataset is synthetic. Harmonization is greedy nearest-neighbour matching. The fire-likelihood score is a heuristic, not a calibrated probability. Detections can be delayed by cloud cover, and “no detection” does not mean “no fire”.

9. System Architecture & Security

To ensure high performance and protect sensitive credentials, the application is built on a Node.js Backend-for-Frontend (BFF) architecture:

  • API Key Protection: The BFF acts as a secure proxy. The NASA FIRMS API key is stored on the server and is never exposed to the browser's developer tools or the end user.
  • Caching: The backend implements an in-memory LRU cache. If multiple users request the same bounding box and date range, the server returns the cached result instead of hitting NASA's API rate limits.
  • Graceful Fallback: If the NASA API fails (e.g., network issues or exceeding the 5-day limit), the frontend is programmed to seamlessly load the synthetic demo dataset. This ensures the application never shows a "broken" state during a presentation.

10. Edge Cases & Geographic Limitations

  • Antimeridian Crossing (180° line): The current implementation uses a standard bounding box. Fires crossing the International Date Line (e.g., near Fiji or the Russian Far East) might not render correctly if a bounding box spans from +179° to -179°.
  • High Latitudes: While the Haversine formula correctly calculates distances on a sphere, the 0.05° grid bucketing used for optimization becomes distorted near the poles (where longitude lines converge). For Arctic regions, a dynamic grid size would be required.
  • Time Zones: All times are strictly parsed and displayed in UTC to avoid ambiguity across different global time zones.

11. Practical Impact & Use Cases

Why does harmonizing MODIS and VIIRS matter in the real world?

  • Firefighters & First Responders: Can use the harmonized map to spot small, newly ignited fires that MODIS alone would miss due to its coarser resolution, allowing for faster dispatch and containment.
  • Climate Researchers: Can filter out persistent industrial flares and volcanoes to get a cleaner dataset for calculating annual carbon emissions and tracking wildfire trends.
  • Local Governments: The "Anomaly Watch" feature allows authorities to quickly identify days with unusually high fire activity and compare regions for resource allocation.

12. Future Work & Roadmap

If we had more time, we would implement the following enhancements:

  • Advanced Clustering: Replace the current greedy nearest-neighbor algorithm with ST-DBSCAN or the Hungarian algorithm for mathematically optimal global matching.
  • Historical Baseline: Integrate standard-science-quality data (not just NRT) to build a 10-year historical baseline for better anomaly detection.
  • Wind Integration: Overlay wind direction and speed data to predict how the detected fires might spread.
  • Sensor Agnostic: Add support for geostationary satellites (e.g., GOES) which provide updates every 10-15 minutes, perfect for early fire detection.
  • Desktop Application: Develop a standalone offline desktop version (e.g., using Electron or Tauri) with local file support, allowing users to drag-and-drop and analyze their own geospatial data in .json, .csv, and .shp (Shapefile) formats.

13. Sources and references

The methods and design choices on this page rest on the publications, NASA documentation and open tools below. For each source we note what we took from it.

Scientific publications: fire detection algorithms

  • Giglio, L., Schroeder, W., & Justice, C. O. (2016). The collection 6 MODIS active fire detection algorithm and fire products. Remote Sensing of Environment, 178, 31–41. doi:10.1016/j.rse.2016.02.054 What we used: the description of the MODIS Collection 6 active fire detection algorithm, including its contextual and absolute threshold tests and the procedures that reject false alarms (for example sun glint and coastal areas). Together with the 1 km pixel size, this explains why MODIS has coarser resolution and tends to miss small fires.
  • Schroeder, W., Oliva, P., Giglio, L., & Csiszar, I. A. (2014). The new VIIRS 375 m active fire detection data product: Algorithm description and initial assessment. Remote Sensing of Environment, 143, 85–96. doi:10.1016/j.rse.2013.12.008 What we used: the rationale for the 375 m VIIRS data, which give more detailed and more coherent mapping than MODIS, especially for small and low-intensity fires. This is the key source for why the two sensors have to be harmonized.

NASA data and documentation

  • NASA FIRMS (Fire Information for Resource Management System). firms.modaps.eosdis.nasa.gov What we used: the direct source of all satellite detections (MODIS and VIIRS) in near real time (NRT). The FIRMS documentation also describes the differences between the data fields — for example, MODIS confidence is a percentage while VIIRS confidence is a class (low / nominal / high) — which we handled when normalizing the data on the backend (see section 2).
  • NASA Earthdata. earthdata.nasa.gov What we used: product specifications such as VNP14IMG_NRT (VIIRS, 375 m), which helped us understand the structure and format of the input data.

Clustering methodology

  • Studies on ST-DBSCAN and spatio-temporal clustering (2026). What we used: the rationale for grouping scattered points into events. The project implements a simplified greedy algorithm (section 3), but it follows the same principle as ST-DBSCAN — spatio-temporal density — which is widely used to find dense groups of events and filter out noise.
  • FireCluster (2026). A multi-source satellite active fire data clustering algorithm for comprehensive wildfire event identification. What we used: the idea that detections from different sources (MODIS and VIIRS) must be considered together to identify complex fire events, which directly matches the goal of this project.

Challenge description

  • Official description of the challenge Harmonization of MODIS and VIIRS Hot Spots (NASA Space Apps Challenge 2026). What we used: the problem statement — merge the records of the two sensors to understand when and where fires occurred, and build a tool for analysing historical activity and spotting anomalies.

Visualization technologies

  • Leaflet.js (with the Leaflet.markercluster plugin), Chart.js, OpenStreetMap and Esri map tiles. What we used: the libraries and map services behind the interactive map, the charts and the base maps with administrative borders and English labels.
